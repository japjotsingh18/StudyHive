# Phase 4 — API Design

> **Revision gate:** ADR-0003 was accepted after this draft. Part 2 must replace session-only core terminology with Activity contracts and add Campus Presence/Need Help Now APIs before this contract is approved or generated.

## 1. Contract principles

- Base URL: `/v1`.
- JSON over HTTPS; UTF-8; `snake_case` fields.
- OpenAPI 3.1 generated by FastAPI is the contract source for documentation and TypeScript client generation.
- Resource nouns in plural; commands are explicit subresources/actions when a plain CRUD update would hide a state transition.
- Server timestamps are RFC 3339 UTC (`2026-08-03T19:00:00Z`); sessions also return IANA timezone.
- IDs are opaque strings. Clients do not infer order or entity type from IDs.
- Additive changes are allowed within `v1`; breaking changes require a new version and migration window.
- All list orderings include a unique stable tie-breaker.

## 2. Authentication

Authenticated requests send a token/session issued through the configured identity provider:

```http
Authorization: Bearer <token>
```

The API validates the provider-specific signature/session, issuer, audience, expiry, authorized party, and user status through an identity adapter. Authentication proves identity; endpoint policies separately validate tenant/university verification, memberships, roles, visibility, blocks, and ownership.

Identity-provider callbacks/webhooks use a dedicated namespaced endpoint such as `/v1/webhooks/identity/{provider}` with provider signature verification, timestamp tolerance, raw-body validation, and event-ID idempotency. Webhooks do not share browser auth behavior.

## 3. Common headers

| Header | Direction | Use |
| --- | --- | --- |
| `Authorization` | request | configured-provider/application bearer token where the selected profile uses bearer auth |
| `Idempotency-Key` | request | required on join, leave, confirmation, check-in, create, and cancellation commands |
| `If-Match` | request | optional/required version precondition on material edits |
| `X-Request-ID` | both | client-provided safe ID or server-generated correlation ID |
| `Retry-After` | response | rate limits or temporary service unavailability |
| `ETag` | response | versioned resource cache/concurrency token |

Idempotency keys are scoped to authenticated user and route fingerprint, retained for a bounded period, and reject reuse with a different request hash.

## 4. Response shapes

### Single resource

The resource is returned directly; transport metadata uses headers.

```json
{
  "id": "opaque-id",
  "title": "CSE 340 exam review",
  "status": "scheduled",
  "version": 4,
  "created_at": "2026-08-03T19:00:00Z",
  "updated_at": "2026-08-03T19:04:00Z"
}
```

### Cursor collection

```json
{
  "items": [],
  "page": {
    "next_cursor": null,
    "has_more": false
  }
}
```

Cursors are opaque, signed/base64url tokens containing query version and stable sort position. Maximum `limit` is policy-defined (default 20, max 100). Changing filters or sort invalidates a cursor.

### Error response

Use `application/problem+json` compatible with RFC 9457:

```json
{
  "type": "https://docs.studyhang.org/problems/session-full",
  "title": "Session is full",
  "status": 409,
  "detail": "Join the waitlist to be notified if a seat opens.",
  "code": "session_full",
  "instance": "/v1/sessions/opaque-id/participants",
  "request_id": "req_opaque",
  "errors": []
}
```

Validation adds safe field entries:

```json
{
  "field": "starts_at",
  "code": "must_be_future",
  "message": "Start time must be in the future."
}
```

Never expose stack traces, SQL, provider tokens, user existence across privacy boundaries, or raw internal exceptions.

## 5. Status code policy

| Status | Meaning |
| --- | --- |
| `200` | successful read/update/command with response |
| `201` | created; includes `Location` |
| `202` | accepted asynchronous operation, e.g. export |
| `204` | successful no-content operation |
| `400` | malformed request outside schema validation |
| `401` | missing/invalid authentication |
| `403` | authenticated but not authorized |
| `404` | absent or intentionally concealed resource |
| `409` | lifecycle, capacity, duplicate, or idempotency conflict |
| `412` | failed `If-Match` precondition |
| `422` | request validation failure |
| `429` | rate limited |
| `503` | temporary dependency/service degradation |

## 6. Filtering, sorting, and search

Filters use explicit query parameters, repeated where plural:

```text
GET /v1/sessions?course_id=...&status=scheduled&tag=exam_review&starts_after=...&starts_before=...&has_capacity=true&sort=starts_at&limit=20
```

Rules:

- endpoints document allowed filters and sorts; arbitrary field expressions are rejected;
- `sort=-created_at` means descending; only one or a small documented combination is supported;
- text query is `q`, normalized and length-limited;
- location/time filters return their interpretation in applied-filter metadata only if ambiguity exists;
- all queries apply authorization before pagination to avoid count/timing leaks;
- MVP avoids exact total counts on high-churn feeds.

## 7. Resource model

### Identity and onboarding

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/me` | Current domain user, profile summary, onboarding state |
| `PATCH` | `/me/profile` | Update allowed profile fields with version check |
| `PUT` | `/me/study-styles` | Replace selected styles |
| `GET` | `/me/privacy` | Field visibility settings |
| `PATCH` | `/me/privacy` | Update visibility settings |
| `GET` | `/me/notification-preferences` | Preferences and quiet hours |
| `PATCH` | `/me/notification-preferences` | Update preferences |
| `POST` | `/me/institutional-email/verifications` | Start/attach verification flow |
| `POST` | `/me/push-subscriptions` | Register FCM subscription |
| `DELETE` | `/me/push-subscriptions/{id}` | Revoke device subscription |
| `POST` | `/me/data-exports` | Start export |
| `POST` | `/me/deletion-requests` | Start account deletion workflow |

`GET /users/{user_id}` returns a policy-filtered public/university profile. It never returns email, exact reliability events, auth IDs, moderation status, or hidden course membership.

### Universities and academic catalog

| --- | --- | --- |

Catalog moderator endpoints live under `/admin/catalog/...`, require scoped roles, and are separately documented to avoid mixing operator contracts with student API.

### Sessions

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/sessions` | Discovery list with filters/sort/cursor |
| `POST` | `/sessions` | Create scheduled session and host participation |
| `GET` | `/sessions/{id}` | Policy-filtered detail |

Create request includes `course_id`, title, description, `location_id` or approved structured location, start/end, timezone, capacity, visibility, tags, and accessibility details. Server rejects unknown fields by default for commands.

### RSVP and attendance commands

| Method | Path | Body/action |
| --- | --- | --- |
| `POST` | `/sessions/{id}/participants/me/confirmation` | `{ "response": "yes" | "no", "participant_version": 3 }` |
| `POST` | `/sessions/{id}/participants/me/waitlist-offer` | `{ "response": "accept" | "decline" }` |

| `POST` | `/sessions/{id}/start` | Host explicit start when policy permits |
| `POST` | `/sessions/{id}/complete` | Host explicit completion |

These are commands because each has lifecycle rules, side effects, audit history, and idempotency behavior. Clients cannot set raw `participant.state` or `session.status` through generic PATCH.

### Dashboard and discovery

| Method | Path | Purpose |
| --- | --- | --- |

`/dashboard` is a composition endpoint optimized for initial render, not a dumping ground. Each section is bounded, includes a continuation link/cursor when relevant, and may fail independently only if the response contract explicitly models that state.

### P1 course content and chat

Reserved resource families:

- `/courses/{id}/posts`, `/posts/{id}/comments`;
- `/courses/{id}/notes`, `/notes/{id}/comments`, reactions/bookmarks;
- `/sessions/{id}/messages`, message attachments/reactions/pins;
- `/uploads/intents`, `/assets/{id}`.

They are not part of the MVP contract and should not appear in generated clients until implemented.

## 8. Example session join

Request:

```http
POST /v1/sessions/s_123/participants HTTP/1.1
Authorization: Bearer …
Idempotency-Key: 0198-example
Content-Type: application/json

{}
```

Confirmed response:

```json
{
  "id": "sp_123",
  "session_id": "s_123",
  "user_id": "u_123",
  "role": "participant",
  "state": "confirmed",
  "waitlist_position": null,
  "confirmation_due_at": "2026-08-04T16:00:00Z",
  "version": 1,
  "created_at": "2026-08-03T19:00:00Z"
}
```

If capacity fills during the request, the same successful endpoint returns a participant with `state: "waitlisted"` and position. A `409 session_full` is used only when waitlisting is disabled.

## 9. WebSocket protocol

Connection: `wss://api.example/v1/ws`. Authentication uses a short-lived token in the supported secure handshake mechanism; never persist it in query logs.

Client messages:

```json
{ "type": "subscribe", "channel": "session", "resource_id": "s_123" }
```

Server envelope:

```json
{
  "event_id": "evt_123",
  "type": "session.participant.updated.v1",
  "aggregate_id": "s_123",
  "aggregate_version": 18,
  "occurred_at": "2026-08-03T19:00:00Z",
  "data": {
    "participant_id": "sp_123",
    "state": "arrived",
    "participant_version": 5
  }
}
```

Protocol behavior:

- authorization is checked on subscribe and when relevant membership changes;
- heartbeat/pong detects stale connections;
- per-connection/channel limits prevent subscription abuse;
- clients ignore duplicates by event ID/version;
- a version gap triggers REST refetch;
- server may send `resync_required` instead of replay;
- sensitive host roster payloads are never broadcast to ordinary viewers.

## 10. Validation policy

- Requests reject unknown command fields.
- Text is Unicode-normalized, length-bounded, and rendered safely; rich text has an explicit sanitized format.
- Start/end validation uses server clock and session timezone; DST ambiguity/nonexistence is surfaced.
- Course/section/location relationships are verified server-side.
- URL fields permit only approved schemes and are normalized.
- File size/type/hash are validated before and after direct upload.
- Enums return stable machine codes; display copy stays client/localization owned.
- Pydantic schemas are split into command, resource, and internal models to prevent mass assignment.

## 11. Rate limiting

Layered token buckets use IP for unauthenticated traffic and user + route class for authenticated traffic. Exact values are configuration, not contract.

Classes:

- ordinary reads;
- search/autocomplete;
- session mutations and RSVP commands;
- reports/blocks;
- upload intents/bytes;
- message/feed writes (P1);
- webhooks by provider signature plus infrastructure controls.

Responses include `429`, `Retry-After`, safe limit metadata where useful, and correlation ID. Rate limiting never silently changes a business state.

## 12. Caching and concurrency

- Public/verified catalog reads may use `Cache-Control` and ETag.
- Personalized responses are `private`/non-shared and vary safely on authorization.
- Material session edits require `If-Match`; stale clients receive `412` with current version/link.
- Commands carry aggregate/participant version in the body where UI decisions depend on a displayed state.
- Optimistic UI rolls back or refetches on `409`/`412`; capacity is never optimistic server-side.

## 13. API security and privacy review

For every endpoint, tests cover:

- unauthenticated, unverified, wrong-university, non-member, blocked, suspended, owner/host, moderator, and admin actors as applicable;
- hidden versus absent resource behavior;
- over-posting and ID substitution;
- cursor tampering and authorization changes between pages;
- rate limits and idempotency conflicts;
- redaction of sensitive fields from response and logs.

## 14. Documentation and testing

- OpenAPI examples cover success plus primary problem codes.
- Generated TypeScript client is checked for drift in CI.
- Schemathesis/property tests exercise OpenAPI validation.
- Consumer contract tests cover Next.js client assumptions.
- State-machine tests use generated legal/illegal transitions.
- API docs include an auth setup guide, pagination guide, errors catalog, webhook verification, and realtime protocol.

## 15. API acceptance checklist

- [ ] Every P0 user action maps to one documented endpoint/command.
- [ ] Every collection has a stable cursor and bounded limit.
- [ ] Error codes are stable, safe, and actionable.
- [ ] Join/RSVP/attendance commands are idempotent under retries.
- [ ] OpenAPI contains no internal/admin-only schema leakage.
- [ ] Realtime authorization and resync behavior pass integration tests.
- [ ] Breaking-change and deprecation process is documented before beta.
